# Kindle 设备端

根目录 `dashboard.py` 是服务端图片生成器，行为不变；本目录只保存设备运行源码，不含私人配置、图片、日志、固件、越狱组件或第三方二进制。

## 目录与依赖

将下面两个目录的**内容**分别合并到 Kindle USB 根目录的同名目录；不要把外层 `kindle` 一起复制。USB 根目录在设备上对应 `/mnt/us`：

```text
documents/
  calendar-manual-refresh.sh       手动下载并显示；首次建立缓存
  calendar-dedicated-start.sh      手动启用专用模式
  calendar-dedicated-recover.sh    退出及恢复
kindle-dashboard/
  calendar-dedicated.sh           控制器、守护与触摸监听
  calendar-auto-refresh.sh        共用单次刷新 worker
  calendar-config.sh              数据配置读取库
  calendar-lock.sh                共用内核锁库
  config.example.conf            空白模板
  config.local.conf              自己在本地创建；禁止提交
  image-auth.example.conf        动态模式空白凭据模板
  image-auth.local.conf          仅动态模式需要；自己创建，禁止提交
```

需要已安装、可从书库运行 shell 入口的 libkh，以及可执行的 `/mnt/us/libkh/bin/fbink`；这些依赖不在本仓库分发。还需要设备现有的 `curl`（HTTPS、证书校验及协议限制支持）、有效 CA/系统时间、LIPC、Upstart 和脚本列出的系统命令。互斥要求 Linux `flock -n FD`（非阻塞、锁随打开的文件描述继承）以及 `nohup setsid /bin/sh` 保留该描述符；不能只凭命令同名推断兼容。缺少或不支持所需 `flock` 时，在修改 GUI 或缓存前明确拒绝，没有 `mkdir`/超时删锁回退。不会自动安装或更新任何依赖。

专用模式针对 PW3 的已核验硬件接口：`max77696-rtc.0` 相对 RTC 闹钟、`/sys/power/state` 的真实内核 suspend、含休眠计数的 `/proc/uptime`、`lab126_gui` 等服务，以及 `/dev/input/event1` 的 `cyttsp4_mt` 触屏（ARM32、16 字节 `input_event`）。启动会核对接口，不按营销型号或固件版本推断兼容性；**不保证所有 PW3 或固件都能使用**。

## 本地配置与首次使用

1. 在本地将 `kindle-dashboard/config.example.conf` 复制为同目录 `config.local.conf`，只在该文件填入真实值。Windows 编辑器使用 UTF-8 无 BOM、LF 换行。
2. `IMAGE_URL` 填可直接下载 PNG 的 HTTPS 地址；`WIFI_SSID` 填 Kindle 已保存网络的完整名称（1–32 字节，可含空格）。两个字段都必填，没有默认下载地址。Wi-Fi 密码通过 Kindle 自身设置保存，不放在此文件。
3. 将 `documents/` 和 `kindle-dashboard/` 合并复制到 USB 根目录，避免覆盖自己的其他文件。不要部署本目录说明、测试或忽略规则。
4. 安全弹出 USB，在 Kindle 上保持唤醒并连接已保存的 Wi-Fi，从书库打开“手动刷新日程”。首次成功后会创建 `/mnt/us/kindle-dashboard/dashboard.png`。
5. 已有成功缓存、网络连接正常时，打开“启用日程专用模式（半小时）”。不要在 USB 存储模式下启动。

配置是严格的 `KEY=value` **数据**，不是 shell 脚本：不要写 `export`，不要给值加外层引号，不展开环境变量或命令。允许必填的 `IMAGE_URL`、`WIFI_SSID` 和可选的 `IMAGE_MODE`，各最多出现一次；允许空行与以 `#` 开头的整行注释。不支持行尾注释。URL 的查询字符串按原样传递（包括 `&`、`=`、`%` 等），禁止空白、反斜杠和 authority 中的用户名/密码；需要的特殊字符应按 URL 规则编码。SSID 的空格原样保留。配置错误会输出不含真实值的错误，且在停止 GUI 或更新缓存前失败。字段参考为 `kindle-dashboard/config.schema.json`；设备读取的仍是 `.conf` 数据，不读取 JSON Schema。

`config.local.conf`、运行日志、PNG 和临时文件已被本目录的忽略规则排除；空白模板不忽略。忽略规则不是保密保证，不要强制添加私人文件，不要公开运行时捕获内容。

### 可选：服务端动态 PNG

默认省略 `IMAGE_MODE` 或写 `IMAGE_MODE=static` 时，仍使用原来的 HTTPS GET，可跟随最多 5 次 HTTPS 跳转，不需要新凭据。动态服务必须由使用者另行提供；本仓库不部署该 HTTP 服务，不改变已有静态原图、分享链接或服务端自动更新。

接入支持电量请求的服务时，将本地 `IMAGE_URL` 改为该服务地址，并显式设置：

```ini
IMAGE_MODE=dynamic
IMAGE_URL=https://example.invalid/image
WIFI_SSID=fixture-network
```

动态 URL 额外禁止双引号和 `#` 片段。将 `image-auth.example.conf` 复制为同目录 `image-auth.local.conf`，在安全的本地编辑器中填入独立 Bearer，**不要在命令行、shell 历史、聊天、日志或 PR 中填写真实值**。该文件只允许一行 `BEARER_TOKEN=` 后接非空值，不加引号、空格或注释，使用 LF 而非 CRLF；值只接受 RFC 6750 的字母、数字、`-._~+/` 和末尾 `=`，整个文件不超过 4096 字节。空模板、缺失、符号链接、控制字符、额外行或注入内容均拒绝，不退回静态 GET。

worker 使用已有 LIPC 严格校验电量 `0..100` 与充电值 `0/1`，发送一次逻辑请求 `POST` JSON，例如 `{"battery":73,"charging":true}`。`charging` 是布尔值而非字符串。显式发送 `Content-Type: application/json` 并禁用 `Expect:`，兼容拒绝 `100-continue` 的服务。动态模式**不跟随任何重定向**，保留严格 HTTPS/TLS 验证、默认 curlrc 禁用、超时和原联网预算；400/401/403 等 HTTP 错误不重试，仅原有瞬时传输故障可在预算内重试。不发额外静态 GET，不使用 cookie，不添加定时或唤醒。

Bearer 不经 `source`/`eval`、环境变量或命令参数传递：读取数据后写入独占的 `/tmp/calendar-image-auth.XXXXXX/request.conf`，由 `curl --config` 读取。该目录在 `umask 077` 下创建为 `0700`，请求配置为 `0600`；下载仍在原同文件系统工作目录，确保缓存原子替换。正常完成、超时及可捕获信号取消时先终止精确 PID/启动时间的子进程，再删除本次私有请求文件。SIGKILL/断电无法执行清理，可能留下私人临时目录，禁止打包或公开；不自动删除不明目录或活跃锁。

**USB 存储通常是 FAT，不能保证持久凭据的 POSIX `0600` 权限**；能读取 USB/设备存储的人可能取得该凭据。请保护设备、电脑和备份，只授予该接口必要权限，定期轮换凭据，不把 FAT 上的 `chmod` 当作隔离保证。`--start` 在私有 `/tmp/calendar-dedicated` 中同时保存配置和 `0600` 凭据快照，活动会话与 worker 从快照读取；USB 上修改不会热更新。静态模式不复制凭据，下一次正常启动按固定清单清除旧快照。退出与恢复始终不依赖配置或 Bearer。

本地 `dashboard.png` 现在就是**服务端返回的完整 PNG**；客户端不改像素、不叠字，不需要新的显示库、图片编辑工具或 native 依赖。相同响应 SHA 时，专用模式仍零 FBInk；独立手动入口仍强制重画。服务端因电量/充电变化返回不同字节时，它就是一张新图，会显示并提交，即使日程本身没变。启动和显示失败恢复只重画已有完整缓存，不为显示缓存联网。仅使用原 FBInk `-q -c -f -w -V -g file=...,w=-1,h=-1` 路径，不要求图片像素尺寸等于物理帧缓冲。

## 专用模式行为

只通过手动入口启用；没有开机钩子、系统配置修改、自动安装或设备部署。启用后停止 GUI、防止原生屏保、关闭前光并显示缓存。每个时隙之间通过已核验 RTC 闹钟进入真实内核休眠，独立守护进程用期限租约监控运行状态并负责异常恢复。

自动刷新为 **UTC+8，06:30–22:00，每半小时一次**。启动时先显示缓存并等待下个时隙；22:00 后睡至次日 06:30。超过时隙 120 秒不补下载。电源键唤醒后，短暂等待触摸；无操作则继续等待原时隙，不把普通唤醒当作刷新请求。

单指短按后松开请求手动刷新，多次请求合并，不并发启动 worker；**单指按住至少 2 秒再松开退出**。多指操作忽略：按 slot 和 tracking ID 维护活动触点，只要出现多指，必须等到全部触点释放后才能识别新的单指手势；中途松开或换指不会重新启用短按刷新或长按退出。触摸使用批量读取及 MT/BTN_TOUCH 去重；只有释放事件的唤醒不产生刷新，时间戳倒退会丢弃当前接触周期。事件丢失或接触持续 30 秒仍触发安全恢复（不是有效长按）。专用模式内的手动刷新只跳过安静时段，仍核验直接父进程 PID/启动时间、所有权标记、active 状态及电量。

电量未知，或电量不超过 20% 且未充电，均不联网，保留缓存。单次联网预算最多 60 秒，连接就绪轮询最多 20 秒且包含在联网预算内。所有模式保留严格 HTTPS/TLS 校验（仅静态模式允许 HTTPS 跳转），不提供关闭证书校验的回退；校验 HTTP 200、PNG 类型、45 字节至 5 MiB 大小和 1072×1448 的 8 位灰度 IHDR（标准压缩/滤波，interlace 0 或 1）。新图片先由 FBInk 成功解码显示，再同文件系统原子替换缓存。下载/验证失败保留旧缓存；显示失败可能已改变屏幕，专用控制器会尝试重画旧缓存。

独立“手动刷新日程”是本次泛化改写，复用同一 worker：要求设备唤醒、专用模式完全退出，使用相同电量与下载保护，可在任何时段运行；即使图片未变化也重画，便于首次显示或回到日程页。它不会停止 GUI、禁止原生休眠或修改前光，与专用模式的单指刷新不是同一入口。

## 退出、更新与故障

长按松开退出会恢复 GUI、原前光亮度与原生休眠，并返回 Home。异常后可从书库运行“退出日程专用模式”；恢复不依赖私人配置，即使配置丢失仍可尝试恢复。不能恢复时请保留现场并诊断，不要删除活跃进程的锁或强行重复启动。已提交的 RTC 闹钟可能还唤醒一次。

从旧版升级前，先用旧入口退出并确认回到正常界面，再正常重启设备，之后连接 USB 替换文件。重启不是恢复出厂设置，也不是固件升级。应一起更新 `calendar-dedicated.sh`、`calendar-auto-refresh.sh`、`calendar-config.sh`、`calendar-lock.sh` 及 `documents/` 的三个入口，保留有效的私人 `config.local.conf`；不要另留重复的旧命名入口来启动旧版本。安全弹出后重新启用。`--start` 会将控制器、worker、配置库、锁库及私人配置一起复制到 `/tmp/calendar-dedicated`，经 `nohup setsid` 隔离启动，以免 GUI 停止信号杀死书库启动器。活动会话读取该快照，USB 上的修改不会热更新；worker 始终为控制器直接子进程。恢复状态及这份私人快照留在内存临时目录，下一次正常启动按固定清单清理。

### 并发、强杀与锁恢复

新版使用两个固定的普通文件：`/tmp/calendar-dedicated.flock`（FD 9，整个专用会话的生命周期）和 `/tmp/calendar-auto-refresh.flock`（FD 8，刷新及恢复资源）。**文件存在不代表持锁，也不能通过删除文件来解锁**。脚本不删除、不改名这两个 inode，也不执行 `flock -u`；即使进程已退出，空锁文件保留也是正常状态。

成功的非阻塞 `flock` 是取得互斥的时刻；最后一个继承该打开文件描述的进程关闭 FD 或退出，才是释放时刻。进程 PID/启动时间仍用于授权、存活判断及精确发信号，但绝不用于“认定过期后删锁”。因此 PID 复用、尚未写入 owner 就被强杀、两个恢复者同时重试，都不涉及共享路径的检查后删除竞争。

启动者在检查旧状态、清理及复制之前取得 FD 9，并一直传给控制器、守护进程、触摸监听及其命令。锁有意保留到整个会话及后代结束，不在发出后台命令时释放；首次启动与 `restored` 目录重启同样互斥。第二个启动者明确收到 `LOCK_BUSY`，不会清理或覆盖第一个实例。启动者在复制中退出时，如果没有控制器接管，后续会提示先恢复；运行恢复入口后才能重新启动。

所有非专用 worker（包括独立 `--manual`）按 FD 9 → FD 8 的顺序取得锁；已授权的专用 worker 继承控制器的 FD 9，再取得 FD 8。worker 的命令继承资源锁，故 worker 被 SIGKILL 后，只要其命令仍持有 FD，另一个刷新或界面恢复就不能抢占。正常退出仅关闭当前进程自己的 FD，不解除后代仍持有的锁。取消子进程后，控制器/守护在恢复 GUI、亮度、原生休眠及 Home 前也必须取得资源锁。

`--stop`/`--recover` 遇到活跃新版会话时，只向已核验 PID、启动时间及生命周期 FD 的控制器请求退出，由控制器在自己的运行目录写标记；不会由另一个启动器越过互斥修改共享文件。交接中的启动者、守护或孤儿命令仍持锁而控制器身份不可确认时，会明确拒绝并提示等待，不假称恢复成功。如果资源仍忙或状态无法确认，保留未恢复状态；等命令退出后再运行恢复入口。持续不明的锁状态应保留现场诊断，不能删除锁文件强行运行。

**旧版迁移必须离线完成**：旧 `/tmp/calendar-auto-refresh.lock` 目录没有可证明的 owner，不能因为它“很旧”、PID 不存在或缺少文件就认定可删。存在旧锁时新版 worker、启动及资源恢复会输出 `LOCK_LEGACY` 并拒绝操作。升级前先用旧版正常退出并完成恢复，再正常重启设备，确认旧进程已终止且临时状态重建后才使用新版；不要同时运行旧快照与新版，不手工删除不明旧锁。这里的重启是由用户执行的迁移步骤，脚本不重启设备，也不添加开机钩子。

设备日志位于 `/mnt/us/kindle-dashboard/`（`dedicated-schedule.log`、`dedicated-refresh.log`、`manual-refresh.log`）。临时命令输出可能含下载地址、网络信息等隐私，排障前先脱敏。worker 中保留的无参数原生屏保及 `--dedicated-trial` 分支只是旧逻辑兼容，不是推荐的联网或生产启动路径，不要给它们添加定时/开机任务。

## 本机开发检查

仓库现有 Python `unittest` 可运行隔离检查：

```text
python -m unittest -v test_kindle test_kindle_dynamic test_kindle_locks
```

`test_kindle` 需要现有 POSIX `sh`（Windows 可使用 Git 附带版本；未在 PATH 时用环境变量 `KINDLE_TEST_SH` 指定本机可执行文件）。`test_kindle_locks` 另外需要真实 Linux `/proc`、`flock`、`nohup`、`setsid` 等既有命令；非 Linux 环境明确跳过，不把模拟锁当作内核并发验证。

锁测试从当前源码提取函数和启动／恢复分支，只使用新建的 `/tmp/kindle-lock-fixture.XXXXXX` 合成目录，替换设备副作用、不联网、不访问 USB或实际日程锁。每个受控屏障最多 90 秒，套件看门狗最多 900 秒；失败会输出用例名和有限合成日志，再按精确 PID／启动时间清理。直接子进程的强杀用例必须确认存活目标收到 SIGKILL、短时限内退出且 `wait` 返回 `137`，不能把自然超时退出算作强杀通过。
