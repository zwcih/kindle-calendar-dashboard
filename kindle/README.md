# Kindle 设备端

根目录 `dashboard.py` 是服务端图片生成器，行为不变；本目录只保存设备运行源码，不含私人配置、图片、日志、固件、越狱组件或第三方二进制。

## 目录与依赖

将下面两个目录的**内容**分别合并到 Kindle USB 根目录的同名目录；不要把外层 `kindle` 一起复制。USB 根目录在设备上对应 `/mnt/us`：

```text
documents/
  calendar-manual-refresh.sh       手动下载并显示；首次建立缓存
  calendar-dedicated-start.sh      手动启用专用模式
  calendar-dedicated-recover.sh    退出及恢复
kindle-dashboard/
  calendar-dedicated.sh           控制器、守护与触摸监听
  calendar-auto-refresh.sh        共用单次刷新 worker
  calendar-config.sh              数据配置读取库
  calendar-lock.sh                共用内核锁库
  calendar-display.sh             共用本地状态栏、FBInk 与时间记录库
  config.example.conf            空白模板
  config.local.conf              自己在本地创建；禁止提交
```

需要已安装、可从书库运行 shell 入口的 libkh，以及可执行的 `/mnt/us/libkh/bin/fbink`；这些依赖不在本仓库分发。还需要设备现有的 `curl`（HTTPS、证书校验及协议限制支持）、有效 CA/系统时间、LIPC、Upstart 和脚本列出的系统命令。互斥要求 Linux `flock -n FD`（非阻塞、锁随打开的文件描述继承）以及 `nohup setsid /bin/sh` 保留该描述符；不能只凭命令同名推断兼容。缺少或不支持所需 `flock` 时，在修改 GUI 或缓存前明确拒绝，没有 `mkdir`/超时删锁回退。不会自动安装或更新任何依赖。

专用模式针对 PW3 的已核验硬件接口：`max77696-rtc.0` 相对 RTC 闹钟、`/sys/power/state` 的真实内核 suspend、含休眠计数的 `/proc/uptime`、`lab126_gui` 等服务，以及 `/dev/input/event1` 的 `cyttsp4_mt` 触屏（ARM32、16 字节 `input_event`）。启动会核对接口，不按营销型号或固件版本推断兼容性；**不保证所有 PW3 或固件都能使用**。

## 本地配置与首次使用

1. 在本地将 `kindle-dashboard/config.example.conf` 复制为同目录 `config.local.conf`，只在该文件填入真实值。Windows 编辑器使用 UTF-8 无 BOM、LF 换行。
2. `IMAGE_URL` 填可直接下载 PNG 的 HTTPS 地址；`WIFI_SSID` 填 Kindle 已保存网络的完整名称（1–32 字节，可含空格）。两个字段都必填，没有默认下载地址。Wi-Fi 密码通过 Kindle 自身设置保存，不放在此文件。
3. 将 `documents/` 和 `kindle-dashboard/` 合并复制到 USB 根目录，避免覆盖自己的其他文件。不要部署本目录说明、测试或忽略规则。
4. 安全弹出 USB，在 Kindle 上保持唤醒并连接已保存的 Wi-Fi，从书库打开“手动刷新日程”。首次成功后会创建 `/mnt/us/kindle-dashboard/dashboard.png`。
5. 已有成功缓存、网络连接正常时，打开“启用日程专用模式（半小时）”。不要在 USB 存储模式下启动。

配置是严格的 `KEY=value` **数据**，不是 shell 脚本：不要写 `export`，不要给值加外层引号，不展开环境变量或命令。仅允许 `IMAGE_URL` 与 `WIFI_SSID`，各出现一次；允许空行与以 `#` 开头的整行注释。不支持行尾注释。URL 的查询字符串按原样传递（包括 `&`、`=`、`%` 等），禁止空白、反斜杠和 authority 中的用户名/密码；需要的特殊字符应按 URL 规则编码。SSID 的空格原样保留。配置错误会输出不含真实值的错误，且在停止 GUI 或更新缓存前失败。

`config.local.conf`、运行日志、PNG 和临时文件已被本目录的忽略规则排除；空白模板不忽略。忽略规则不是保密保证，不要强制添加私人文件，不要公开运行时捕获内容。

## 专用模式行为

只通过手动入口启用；没有开机钩子、系统配置修改、自动安装或设备部署。启用后停止 GUI、防止原生屏保、关闭前光并显示缓存。每个时隙之间通过已核验 RTC 闹钟进入真实内核休眠，独立守护进程用期限租约监控运行状态并负责异常恢复。

自动刷新为 **UTC+8，06:30–22:00，每半小时一次**。启动时先显示缓存并等待下个时隙；22:00 后睡至次日 06:30。超过时隙 120 秒不补下载。电源键唤醒后，短暂等待触摸；无操作则继续等待原时隙，不把普通唤醒当作刷新请求。

单指短按后松开请求手动刷新，多次请求合并，不并发启动 worker；**单指按住至少 2 秒再松开退出**。多指操作忽略：按 slot 和 tracking ID 维护活动触点，只要出现多指，必须等到全部触点释放后才能识别新的单指手势；中途松开或换指不会重新启用短按刷新或长按退出。触摸使用批量读取及 MT/BTN_TOUCH 去重；只有释放事件的唤醒不产生刷新，时间戳倒退会丢弃当前接触周期。事件丢失或接触持续 30 秒仍触发安全恢复（不是有效长按）。专用模式内的手动刷新只跳过安静时段，仍核验直接父进程 PID/启动时间、所有权标记、active 状态及电量。

电量未知，或电量不超过 20% 且未充电，均不联网，保留缓存。单次联网预算最多 60 秒，连接就绪轮询最多 20 秒且包含在联网预算内。所有模式保留严格 HTTPS 跳转及 TLS 校验，不提供关闭证书校验的回退；校验 HTTP 状态、PNG 类型、45 字节至 5 MiB 大小和 1072×1448 的 8 位灰度 IHDR。新图片先由 FBInk 成功显示，再同文件系统原子替换缓存。下载/验证失败保留旧缓存；显示失败可能已改变屏幕，专用控制器会尝试重画旧缓存。

独立“手动刷新日程”是本次泛化改写，复用同一 worker：要求设备唤醒、专用模式完全退出，使用相同电量与下载保护，可在任何时段运行；即使图片未变化也重画，便于首次显示或回到日程页。它不会停止 GUI、禁止原生休眠或修改前光，与专用模式的单指刷新不是同一入口。

## 本地状态栏与内容更新时间

图片提供方必须为 `1072×1448` 图片预留底部 **36 像素白色状态栏**：`x=0..1071, y=1412..1447`。客户端只在这个矩形内绘制，左侧 `Updated YYYY-MM-DD HH:MM`，右侧电池图标与 `0..100%`，文字使用 FBInk 内建 ASCII 字体。**本次不改服务端图片生成器；未配套留白的现有图片会被覆盖底部内容**，不是已验证兼容。旧的卡片内 `y=1338` 预览方案不再使用；也不需要外部字体包、图像处理程序或服务端电量 API。

独立手动刷新、专用模式单指刷新、自动刷新、启动缓存显示及显示失败后的缓存重画，在**实际整图显示**时复用 `calendar-display.sh`。接近显示完成时重新查询 `com.lab126.powerd battLevel`，只接受严格整数 `0..100`；充电不改变百分比含义。它不是复用联网前低电量保护的旧读数，也不新增 `isCharging` 查询、定时器或额外唤醒。**显示值是最近一次实际整图显示时的采样，不是实时电量**；低电量、安静时段、网络、取消和睡眠保护仍生效。

**专用模式原始图片 SHA 相同时完全跳过显示：零 FBInk 调用，不刷新任何区域，不额外读取电量、不发布 sidecar。**保留屏幕上次电量和内容时间，不因状态栏引入额外刷屏。独立手动入口即使 SHA 相同仍按原行为重画整图；启动和错误恢复也照常显示缓存，这些实际重画才重新采样电量并补画状态栏。

状态栏跟随整图显示时，先清白底再绘制电池和完整文字，最后提交底栏局部屏幕刷新；`100 → 99 → 9 → 0` 不依赖旧字符宽度，也不会保留旧数字。所有新 LIPC／FBInk 命令串行复用当前进程的有界执行器、精确 PID／启动时间和信号保护，继承 FD 9／FD 8。控制器两条缓存显示路径也持资源锁，不与 worker 或恢复并行绘制。整图与状态栏共用一个 30 秒总 deadline，每笔绘制不重置预算；控制器的 worker 外层上限为 120 秒，为原有 60 秒联网、20 秒网络恢复及初始授权留余量，并不延长联网预算或改变取消处理。

`Updated` 为 **UTC+8 的客户端内容显示时间**：只有下载的原始 PNG SHA 改变时，才在整图显示后采样系统日期／时间；状态栏成功绘制、原始缓存原子替换后，将 SHA 与该时间写入 `dashboard.status`。它不是服务器原始编辑时刻、图片生成元数据，也不是最近联网成功时刻。`UNCHANGED`、同 SHA 独立手动重画、启动或恢复缓存都保留原时间。系统时间不可读取或不是合法日期时明确失败，不捏造日期；它仍依赖设备系统时钟准确。

原始 `dashboard.png` 从不写入电量或文字，其 SHA 始终只比较下载原图。`dashboard.status` 是同目录私有运行状态，含原始 SHA 与时间，已忽略且隐私扫描禁止入库。首次升级只有旧缓存、没有记录时显示 `Updated --`。记录损坏或 SHA 不符时记录 `STATUS_TIME_UNKNOWN` 并显示 `--`，不能用开机时间、PNG 文件修改时间或当前时间补造；直到之后实际内容变化并成功完成才建立新时间。

PNG 与 sidecar 各自原子替换，但**两文件不是一个原子事务**：顺序为完整显示 → 原图缓存替换 → 时间记录发布。断电／强杀或第二次替换失败的窗口可能留下新 PNG 与旧记录；加载时必须验证 SHA，失配显示 `--`。PNG 未变时不改 sidecar。下载、PNG 验证、绘制失败不推进持久时间；时间文件准备／发布失败返回 I/O 失败，不能记录 `UPDATED` 成功。发布失败时 PNG 可能已经更新，这一点会明确记录。

电量读取失败／非法或 FBInk 失败返回显示失败（`15`），不冒充 `0%` 或成功；显示失败时缓存未提交，控制器尝试用旧缓存及其绑定时间重新画整图和状态栏。缓存重画也失败则退出并恢复阅读界面。时钟／时间文件 I/O 错误返回 `14`；取消及恢复失败保持原有优先级。批处理失败、原子提交失败或进程被强杀时，屏幕／帧缓冲可能仍是旧内容、部分绘制或临时显示，**不是成功凭据**；独立手动入口报错后需重试。日志只记录阶段／退出码，不打印本机属性或命令原始输出。

### FBInk 能力依据与坐标

区域 `-k` 至少需要官方 **v1.21.0**；旧版同名参数可能直接清全屏，因此不能通过试画来探测。每次实际整图显示前，在同一资源锁和总 deadline 内运行只输出帮助的 `--help`，仅接受其中完整的 `-k, --cls [top=NUM,left=NUM,width=NUM,height=NUM]` 行（兼容已核对的无方括号形式）。帮助失败、超时或不匹配就拒绝绘图；UNCHANGED 连这个探测也不调用。不安装或更新 FBInk。

实现依据官方 [v1.25.0 CLI](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink_cmd.c#L282-L313)、[区域清理 API](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink.h#L1063-L1078) 及 [IBM 字格定义／缩放](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink.c#L4626-L4755)。矩形 `-k` 的坐标是绝对像素；背景色用 `-B`，全部底栏绘制使用 `-b` 只写 framebuffer，末次 `-w -W GC16 -s top=1412,left=0,width=1072,height=36` 才请求该区域更新并等待，不加 `-f`。电量填充宽度为整数向下取整，宽度为零时不调用矩形命令，以免触发空矩形全屏语义。

| 元素 | 实际像素区域 |
| --- | --- |
| 状态栏白底 | `x0 y1412 w1072 h36` |
| 时间文字 | `x12 y1418`，IBM `-S 3`，24×24 字格 |
| 电池外框／内孔 | `x918 y1421 w32 h18`／`x920 y1423 w28 h14`，2px 黑框 |
| 电池端子 | `x951 y1426 w3 h8` |
| 电量填充 | `x922 y1425 w0..25 h10` |
| 百分比 | `x964 y1418 w96 h24`，固定四字格，右对齐，右侧留12px |

IBM 原始字格为 8×8。1072px 宽度配 24px 字格时，[FBInk 仍加 8px 水平修正](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink.c#L1196-L1210)，`-V` 只关闭相应垂直修正；因此文本传入的 `-X` 是 `4` 和 `956`，不是实际的 `12` 和 `964`。`-Y 1418` 为文字顶部，不是 HTML baseline。年月日时间最多24字格，右边界为588，远离电池。没有使用全行 padding、外部字体或旧预览区域。

官方 v1.25.0 的 [CLI 等待分支](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink_cmd.c#L2537-L2548) 存在未传播等待失败返回值的情况；[warning 不受 quiet 开关抑制](https://github.com/NiLuJe/FBInk/blob/v1.25.0/fbink_internal.h#L425-L449)。因此实际绘制均使用 `-q`，**即使退出0，只要捕获到诊断输出也保守认定显示失败**，不把等待 ioctl 错误当作成功。帮助输出单独处理，不使用 syslog 转移诊断。能力探测不是完整设备兼容认证；驱动的物理刷新边缘和残影仍需后续真机验证。

## 退出、更新与故障

长按松开退出会恢复 GUI、原前光亮度与原生休眠，并返回 Home。异常后可从书库运行“退出日程专用模式”；恢复不依赖私人配置，即使配置丢失仍可尝试恢复。不能恢复时请保留现场并诊断，不要删除活跃进程的锁或强行重复启动。已提交的 RTC 闹钟可能还唤醒一次。

从旧版升级前，先用旧入口退出并确认回到正常界面，再正常重启设备，之后连接 USB 替换文件。重启不是恢复出厂设置，也不是固件升级。应一起更新 `calendar-dedicated.sh`、`calendar-auto-refresh.sh`、`calendar-config.sh`、`calendar-lock.sh`、`calendar-display.sh` 及 `documents/` 的三个入口，保留有效的私人 `config.local.conf`；不要另留重复的旧命名入口来启动旧版本。缓存 `dashboard.png` 与时间记录 `dashboard.status` 留在设备上，不导入仓库或发布包。安全弹出后重新启用。`--start` 会将控制器、worker、配置库、锁库、显示库及私人配置一起复制到 `/tmp/calendar-dedicated`，经 `nohup setsid` 隔离启动，以免 GUI 停止信号杀死书库启动器。活动会话读取该快照，USB 上的修改不会热更新；worker 始终为控制器直接子进程。恢复状态及这份私人快照留在内存临时目录，下一次正常启动按固定清单清理。正常 Home／GUI 恢复不需要显示库、时间记录或私人配置，缺失这些文件不能阻断退出。

### 并发、强杀与锁恢复

新版使用两个固定的普通文件：`/tmp/calendar-dedicated.flock`（FD 9，整个专用会话的生命周期）和 `/tmp/calendar-auto-refresh.flock`（FD 8，刷新及恢复资源）。**文件存在不代表持锁，也不能通过删除文件来解锁**。脚本不删除、不改名这两个 inode，也不执行 `flock -u`；即使进程已退出，空锁文件保留也是正常状态。

成功的非阻塞 `flock` 是取得互斥的时刻；最后一个继承该打开文件描述的进程关闭 FD 或退出，才是释放时刻。进程 PID/启动时间仍用于授权、存活判断及精确发信号，但绝不用于“认定过期后删锁”。因此 PID 复用、尚未写入 owner 就被强杀、两个恢复者同时重试，都不涉及共享路径的检查后删除竞争。

启动者在检查旧状态、清理及复制之前取得 FD 9，并一直传给控制器、守护进程、触摸监听及其命令。锁有意保留到整个会话及后代结束，不在发出后台命令时释放；首次启动与 `restored` 目录重启同样互斥。第二个启动者明确收到 `LOCK_BUSY`，不会清理或覆盖第一个实例。启动者在复制中退出时，如果没有控制器接管，后续会提示先恢复；运行恢复入口后才能重新启动。

所有非专用 worker（包括独立 `--manual`）按 FD 9 → FD 8 的顺序取得锁；已授权的专用 worker 继承控制器的 FD 9，再取得 FD 8。worker 的命令继承资源锁，故 worker 被 SIGKILL 后，只要其命令仍持有 FD，另一个刷新或界面恢复就不能抢占。正常退出仅关闭当前进程自己的 FD，不解除后代仍持有的锁。取消子进程后，控制器/守护在恢复 GUI、亮度、原生休眠及 Home 前也必须取得资源锁。

`--stop`/`--recover` 遇到活跃新版会话时，只向已核验 PID、启动时间及生命周期 FD 的控制器请求退出，由控制器在自己的运行目录写标记；不会由另一个启动器越过互斥修改共享文件。交接中的启动者、守护或孤儿命令仍持锁而控制器身份不可确认时，会明确拒绝并提示等待，不假称恢复成功。如果资源仍忙或状态无法确认，保留未恢复状态；等命令退出后再运行恢复入口。持续不明的锁状态应保留现场诊断，不能删除锁文件强行运行。

**旧版迁移必须离线完成**：旧 `/tmp/calendar-auto-refresh.lock` 目录没有可证明的 owner，不能因为它“很旧”、PID 不存在或缺少文件就认定可删。存在旧锁时新版 worker、启动及资源恢复会输出 `LOCK_LEGACY` 并拒绝操作。升级前先用旧版正常退出并完成恢复，再正常重启设备，确认旧进程已终止且临时状态重建后才使用新版；不要同时运行旧快照与新版，不手工删除不明旧锁。这里的重启是由用户执行的迁移步骤，脚本不重启设备，也不添加开机钩子。

设备日志位于 `/mnt/us/kindle-dashboard/`（`dedicated-schedule.log`、`dedicated-refresh.log`、`manual-refresh.log`）。临时命令输出可能含下载地址、网络信息等隐私，排障前先脱敏。worker 中保留的无参数原生屏保及 `--dedicated-trial` 分支只是旧逻辑兼容，不是推荐的联网或生产启动路径，不要给它们添加定时/开机任务。

## 本机开发检查

仓库现有 Python `unittest` 可运行隔离检查：

```text
python -m unittest -v test_kindle test_kindle_display test_kindle_locks
```

`test_kindle` 需要现有 POSIX `sh`（Windows 可使用 Git 附带版本；未在 PATH 时用环境变量 `KINDLE_TEST_SH` 指定本机可执行文件）。`test_kindle_locks` 另外需要真实 Linux `/proc`、`flock`、`nohup`、`setsid` 等既有命令；非 Linux 环境明确跳过，不把模拟锁当作内核并发验证。

`test_kindle_display` 提取共享库及实际入口函数，以合成命令替代 FBInk／LIPC：覆盖严格电量范围、充电无关百分比、位数变化、36px 几何边界、旧版帮助拒绝、退出0但等待告警、共享 deadline、SHA 时间绑定、原图保持与两次原子替换的故障窗口、全部显示／缓存入口及 UNCHANGED 零 FBInk。Linux 子用例用实际有界执行器和 `flock` 验证描述符继承、超时、TERM 和缓存绘制后资源释放／恢复，仍不调用硬件。

锁测试从当前源码提取函数和启动／恢复分支，只使用新建的 `/tmp/kindle-lock-fixture.XXXXXX` 合成目录，替换设备副作用、不联网、不访问 USB或实际日程锁。每个受控屏障最多 90 秒，套件看门狗最多 900 秒；失败会输出用例名和有限合成日志，再按精确 PID／启动时间清理。直接子进程的强杀用例必须确认存活目标收到 SIGKILL、短时限内退出且 `wait` 返回 `137`，不能把自然超时退出算作强杀通过。
